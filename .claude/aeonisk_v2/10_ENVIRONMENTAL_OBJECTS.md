# Spec 10: Environmental Objects & Destructibles

**Priority:** P2 (Wave 3 -- Parallel After Wave 1)
**Status:** Not started
**Dependencies:** None (but 12_DISPLAY depends on this for env object display)
**Estimated Scope:** Medium

---

## Problem Statement

Environmental objects exist in the current system as narrative-only entities.
The DM can spawn doors, terminals, cargo crates, barricades, vehicles, and
other features into the scene, and players see them listed in their entity
prompts. However, these objects cannot be mechanically targeted, damaged, or
destroyed. They have no HP, are not registered in the TargetIDMapper, and
the DamageEffect schema cannot reference them. This creates a fundamental
disconnect: players describe shooting a door or hacking a terminal, the DM
narrates the outcome, but no mechanical state change occurs. The door stays
"locked" forever because no code path can destroy it.

### Concrete Failures from Baseline Sessions

1. **Player declares "shoot the locked door"** -- DM narrates the door
   splintering, but `state["locked"]` remains `True` because no code path
   modifies env object state from combat resolution.

2. **Player targets an env object with tgt_xxxx** -- Impossible, because env
   objects do not receive tgt_xxxx IDs. The player must describe the object
   by name, and the DM must manually interpret that. No structured targeting.

3. **DM narrates "the terminal explodes from the gunfire"** -- Pure flavor
   text. The terminal remains in `current_env_objects` with its original
   state dict unchanged. Future rounds still show it as available.

### Why This Matters

- **ML training data integrity:** Sessions log env objects as present even
  after they are narratively destroyed. Downstream models learn that objects
  are indestructible.
- **Player agency:** Players cannot interact mechanically with the environment.
  Cover, doors, and vehicles are immutable set dressing.
- **DM coherence:** DM must track destruction narratively (error-prone) rather
  than mechanically (deterministic).

## Current Implementation

### EnvironmentalObject dataclass (`shared_state.py:102-127`)

```python
@dataclass
class EnvironmentalObject:
    object_type: EnvironmentalObjectType    # DOOR, TERMINAL, CARGO, etc.
    name: str                               # "Blast Door Alpha"
    description: str                        # "Heavy reinforced door"
    state: Dict[str, Any] = field(...)      # {"locked": True, "health": 50}
    object_id: Optional[str] = None         # Auto-generated: env_xxxx
```

Key observations:
- `state` dict is freeform -- health is sometimes stored there as a convention
  (`state["health"]`) but is NOT a first-class field.
- `object_id` uses `env_xxxx` prefix (4 random alphanumeric), generated by
  `generate_env_object_id()` at line 33.
- No `is_destructible` flag. No `max_health`. No `health` field.

### EnvironmentalObjectType enum (`shared_state.py:54-62`)

Seven object types: DOOR, TERMINAL, CARGO, VEHICLE, BARRIER, STRUCTURE,
EQUIPMENT. These are display/categorization only -- no type has special
mechanical behavior.

### SharedState env object management (`shared_state.py:702-759`)

- `add_env_object()` (line 704): Adds to `current_env_objects`, deduplicates
  by `object_id`.
- `remove_env_object()` (line 722): Removes by `object_id`, returns bool.
- `get_env_object_by_id()` (line 738): Lookup by `object_id`.
- `get_all_env_objects()` (line 753): Returns full list.
- `clear_env_objects()` (line 757): Removes all.

### TargetIDMapper (`target_ids.py`)

- `assign_ids()` (line 75) accepts: `player_agents`, `enemy_agents`,
  `npc_agents`, `vendors`. Environmental objects are NOT in this list.
- `resolve_target()` (line 177) returns `None` for unknown tgt_xxxx IDs,
  with a debug message: "likely env object" (line 208). This is a dead-end --
  the code acknowledges env objects might be targets but does nothing.

### Player entity display (`player.py:2290-2312`)

Env objects are shown to players under "Environmental Features" with their
`object_id` (env_xxxx format) and state dict. Players see:
```
- Blast Door Alpha [ID: env_k3r8] (locked: Yes, health: 50)
```
But they cannot use `env_k3r8` as a target -- it is not a tgt_xxxx ID.

### DM combatant list (`dm.py:7536-7578`)

The combatant list passed to the DM for target ID resolution does NOT include
env objects. Only PCs, enemies, NPCs, and vendors are listed.

### DamageEffect resolution (`dm.py:180-276`)

`_process_structured_damage_effects()` resolves damage targets by:
1. Checking if target starts with `tgt_` (free targeting mode).
2. Falling back to character name matching against enemies and NPCs.
Environmental objects are not checked in either path.

## Design Decisions (User Confirmed)

1. **Objects are targets** -- They receive `tgt_xxxx` IDs and appear in the
   combatant list alongside PCs, enemies, and NPCs.

2. **Interactable = destructible** -- All objects that the DM spawns into the
   scene can be damaged. There is no separate "interactable but indestructible"
   category. If the DM wants an indestructible wall, it is part of the scene
   description, not an EnvironmentalObject.

3. **Objects have HP and descriptive hints** -- First-class `health` and
   `max_health` fields on the dataclass, plus `is_destructible` flag for
   objects that should ignore damage (reinforced structures, etc.).

4. **State transitions on destruction** -- When HP reaches 0, the object's
   `state` dict is updated to reflect destruction (e.g., `locked: False`,
   `destroyed: True`). The object remains in `current_env_objects` but with
   updated state -- it is not removed (a destroyed door is still physically
   present as rubble).

5. **DM controls initial HP** -- The DM decides object health when spawning
   via structured output. Typical defaults: Door 30 HP, Terminal 15 HP,
   Barrier 50 HP, Vehicle 80 HP.

## Proposed Solution

### Phase 1: Schema Changes

#### 1.1 Extend EnvironmentalObject (`shared_state.py`)

```python
@dataclass
class EnvironmentalObject:
    object_type: EnvironmentalObjectType
    name: str
    description: str
    state: Dict[str, Any] = field(default_factory=dict)
    object_id: Optional[str] = None

    # NEW: Destructibility
    health: Optional[int] = None          # Current HP (None = non-destructible)
    max_health: Optional[int] = None      # Maximum HP
    is_destructible: bool = True          # False = ignore all damage

    # NEW: Target integration
    target_id: Optional[str] = None       # Assigned tgt_xxxx when registered

    @property
    def is_destroyed(self) -> bool:
        """Check if object has been destroyed (HP <= 0)."""
        if self.health is None:
            return False
        return self.health <= 0

    def apply_damage(self, amount: int) -> int:
        """
        Apply damage to object. Returns actual damage dealt.
        Returns 0 if non-destructible or already destroyed.
        """
        if not self.is_destructible or self.health is None:
            return 0
        if self.health <= 0:
            return 0  # Already destroyed

        actual = min(amount, self.health)
        self.health -= actual

        # Trigger state change on destruction
        if self.health <= 0:
            self.health = 0
            self._on_destroyed()

        return actual

    def _on_destroyed(self):
        """Update state dict when object is destroyed."""
        self.state['destroyed'] = True
        self.state['functional'] = False

        # Type-specific state changes
        if self.object_type == EnvironmentalObjectType.DOOR:
            self.state['locked'] = False
            self.state['open'] = True
        elif self.object_type == EnvironmentalObjectType.TERMINAL:
            self.state['powered'] = False
            self.state['hacked'] = False
        elif self.object_type == EnvironmentalObjectType.BARRIER:
            self.state['intact'] = False
        elif self.object_type == EnvironmentalObjectType.VEHICLE:
            self.state['operational'] = False
```

### Phase 3: Damage Application

#### 3.1 Update `_process_structured_damage_effects()` (`dm.py:180+`)

After checking enemies and NPCs in the name-based resolution fallback, add
env object resolution. For tgt_xxxx-based resolution, the existing
`target_id_mapper.resolve_target()` will already return the env object once
Phase 2 is complete. The new code handles applying damage:

```python
# After resolving target_entity via tgt_xxxx or name matching:

if target_entity and hasattr(target_entity, 'object_type'):
    # This is an environmental object, not a combatant
    actual_damage = target_entity.apply_damage(damage_amount)
    if actual_damage > 0:
        messages.append(
            f"** {target_entity.name} takes {actual_damage} damage! "
            f"({target_entity.health + actual_damage} -> {target_entity.health} HP)"
        )
        if target_entity.is_destroyed:
            messages.append(f"** {target_entity.name} is DESTROYED!")

            # Log destruction event
            if mechanics and hasattr(mechanics, 'jsonl_logger') and mechanics.jsonl_logger:
                mechanics.jsonl_logger.log_env_object_damage(
                    round_num=current_round,
                    object_id=target_entity.object_id,
                    object_name=target_entity.name,
                    damage_dealt=actual_damage,
                    health_before=target_entity.health + actual_damage,
                    health_after=0,
                    destroyed=True,
                    attacker_id=attacker_id
                )
    elif not target_entity.is_destructible:
        messages.append(f"** {target_entity.name} is impervious to damage!")
    continue  # Skip combatant damage logic
```

### Phase 5: JSONL Logging

Add a new event type `env_object_damage` to the JSONL logger
(`jsonl_logger.py`):

```python
def log_env_object_damage(
    self,
    round_num: int,
    object_id: str,
    object_name: str,
    damage_dealt: int,
    health_before: int,
    health_after: int,
    destroyed: bool,
    attacker_id: str
):
    """Log damage dealt to an environmental object."""
    self._write_event({
        "event_type": "env_object_damage",
        "round": round_num,
        "object_id": object_id,
        "object_name": object_name,
        "damage": {
            "dealt": damage_dealt,
            "health_before": health_before,
            "health_after": health_after
        },
        "destroyed": destroyed,
        "attacker_id": attacker_id,
        "timestamp": self._timestamp()
    })
```

## Open Questions

1. **Should destroyed objects remain targetable?** Current design keeps them
   in `current_env_objects` with `destroyed: True` state but does not re-assign
   target IDs in subsequent rounds. Players can describe interacting with
   rubble narratively but cannot target it mechanically. Is this correct?

2. **Cover mechanics:** Should env objects provide mechanical cover (damage
   reduction for characters behind them)? This would integrate with the
   Condition/barrier system (`protection_amount` field on Condition at
   `shared_types.py:238`). Deferred to a future spec or added here?

3. **Soak for objects:** Should env objects have a soak value (like enemy
   armor) that reduces incoming damage? Current design applies full damage
   with no soak. Objects are simpler/softer targets than armored enemies.

4. **Object interaction beyond damage:** Hacking a terminal, lockpicking a
   door, hotwiring a vehicle -- these are non-combat interactions that should
   also modify object state via structured output. Should this spec cover
   non-damage interactions, or is that a separate spec?

5. **DM-spawned objects during synthesis:** The `EnvObjectSpawn` schema in
   RoundSynthesis needs to be wired into the synthesis processing code. How
   does the DM know what HP to assign? Should we provide defaults per
   `object_type` that the DM can override?

6. **Object removal from scene:** When should destroyed objects be removed
   entirely from `current_env_objects`? Never (they become rubble)? After N
   rounds? Only via explicit DM synthesis directive?

## Migration Notes

### Backward Compatibility

- Existing EnvironmentalObject instances (created before this change) will
  have `health=None`, `max_health=None`, `is_destructible=True`, and
  `target_id=None` by default.
- Objects with `health=None` cannot be damaged (`apply_damage()` returns 0)
  and `is_destroyed` returns False.
- Objects with `health=None` will still appear in player entity display with
  no HP indicator -- behavior identical to current system.
- Existing session configs that spawn env objects via DM narration continue
  to work. HP assignment requires the new `EnvObjectSpawn` structured output
  in RoundSynthesis.
- `assign_ids()` call sites that do not pass `env_objects=` will behave
  identically to today (parameter defaults to `None`).

### Default HP by Object Type (Suggested)

| Object Type | Default HP | Rationale |
|-------------|-----------|-----------|
| DOOR | 30 | Standard interior door, 2-3 rifle hits |
| TERMINAL | 15 | Fragile electronics |
| CARGO | 40 | Reinforced shipping container |
| VEHICLE | 80 | Armored transport |
| BARRIER | 50 | Purpose-built cover |
| STRUCTURE | 100 | Building element (often indestructible) |
| EQUIPMENT | 20 | Miscellaneous machinery |

These defaults would be used when the DM does not specify health in the
`EnvObjectSpawn`. The DM can always override with explicit values.
