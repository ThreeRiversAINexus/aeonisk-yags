# Fixture Management Strategy

## Problem: How to Handle Buggy Fixture Data

When you fix bugs, your test fixtures may contain data generated by the buggy code. This document explains the strategy for managing this.

## Strategy: Keep Both Versions

### Approach 1: Version Your Fixtures

**Recommended for major bug fixes or behavior changes**

```
tests/fixtures/sessions/
├── session_debt_auction_ambush_v1.jsonl      # Original buggy data
├── session_debt_auction_ambush_v2.jsonl      # Regenerated with fix
└── README.md                                  # Explains differences
```

**When to use:**
- Bug significantly changes output structure
- You want to test both old and new behavior
- Historical data is valuable for analysis

**Example:**
```python
@pytest.fixture
def buggy_session_data():
    """Original session data with status effect bug (for regression testing)."""
    return load_fixture("session_debt_auction_ambush_v1.jsonl")

@pytest.fixture
def fixed_session_data():
    """Regenerated session data after bug fix."""
    return load_fixture("session_debt_auction_ambush_v2.jsonl")
```

### Approach 2: Annotate and Keep Original

**Recommended for documentation/analysis purposes**

Keep the original fixture but add metadata explaining known bugs:

```
tests/fixtures/sessions/
├── session_debt_auction_ambush.jsonl         # Original data (has bugs)
└── session_debt_auction_ambush_bugs.json     # Bug annotations
```

**Bug annotation file:**
```json
{
  "fixture": "session_debt_auction_ambush.jsonl",
  "generated": "2025-10-31T10:00:00Z",
  "known_bugs": [
    {
      "bug_id": "status-effect-targeting",
      "severity": "high",
      "description": "Status effects applied to actor instead of target",
      "affected_events": [
        {"event_number": 23, "character": "Riven Ashglow", "issue": "Stunned applied to Riven instead of raiders"}
      ],
      "fixed_in_commit": "abc123",
      "test_file": "tests/unit/test_status_effect_targeting.py"
    }
  ],
  "usage": "Use for regression testing and bug documentation only"
}
```

### Approach 3: Replace After Validation

**Recommended for simple bug fixes with clear improvements**

1. **Before replacing:**
   - Run tests with old fixture → document failures
   - Fix the bug
   - Generate new fixture
   - Verify new fixture has expected behavior
   - Update tests to expect new behavior

2. **Archive old fixture:**
   ```
   tests/fixtures/sessions/archive/
   └── session_debt_auction_ambush_2025-10-31_pre-bugfix.jsonl
   ```

3. **Replace with new:**
   ```
   tests/fixtures/sessions/
   └── session_debt_auction_ambush.jsonl  # New, correct data
   ```

## Recommended Strategy for This Project

### For the Status Effect Targeting Bug:

**Option: Generate New Test Fixture + Keep Original for Documentation**

```
tests/fixtures/sessions/
├── session_debt_auction_ambush.jsonl              # KEEP - Historical value, bug documented
├── session_status_effect_test.jsonl               # NEW - Targeted test for fix
```

**Rationale:**
- Original fixture is valuable for ML training (shows agent behavior under buggy conditions)
- Original fixture documents real session that happened
- New targeted fixture specifically tests the fix
- Bug documentation file explains what to expect in original data

## Best Practices

### 1. Never Silently Replace Fixtures

**❌ Bad:**
```bash
# Generate new fixture
python3 scripts/run_multiagent_session.py config.json > fixture.jsonl
# Overwrite old one (history lost!)
```

**✅ Good:**
```bash
# Archive old version
mv fixture.jsonl fixture_2025-10-31_pre-fix.jsonl
# Generate new version
python3 scripts/run_multiagent_session.py config.json > fixture.jsonl
# Document what changed
echo "Regenerated after fixing bug #123" >> fixture_changelog.txt
```

### 2. Use Fixture Metadata

Add metadata to fixture files:

```jsonl
{"event_type": "metadata", "fixture_version": "2.0", "generated": "2025-10-31T14:00:00Z", "bugs_fixed": ["status-effect-targeting"], "config": "session_config_status_effect_test.json"}
{"event_type": "scenario", ...}
```

### 3. Test Both Old and New Behavior

For critical bugs, write tests that verify:

```python
class TestStatusEffectBugFix:
    """Tests for status effect targeting bug and its fix."""

    def test_original_fixture_has_bug(self):
        """Document that original fixture contains the bug (expected behavior at time of recording)."""
        events = load_fixture("session_debt_auction_ambush.jsonl")
        riven_action = find_event(events, agent="Riven Ashglow", action_contains="telekinetic debris")

        # This is the BUG - but it's what was actually generated
        assert "Condition (Riven Ashglow): Stunned" in riven_action['context']['narration'], \
            "Original fixture should show the bug (for historical accuracy)"

    def test_new_fixture_has_fix(self):
        """Verify new fixture doesn't have the bug."""
        events = load_fixture("session_status_effect_test.jsonl")
        player_action = find_event(events, event_type="action_resolution")

        # This should NOT happen in new fixture
        assert "Condition (Test Caster): Stunned" not in player_action['context']['narration'], \
            "New fixture should NOT show debuff applied to actor"
```

### 4. Document Fixture Lineage

Create a `tests/fixtures/sessions/README.md`:

```markdown
# Session Fixtures

## Active Fixtures

### session_status_effect_test.jsonl
- **Generated:** 2025-10-31
- **Purpose:** Test status effect targeting fix
- **Config:** session_config_status_effect_test.json
- **Expected:** Debuffs applied to enemies, NOT to player
- **Bugs:** None (generated post-fix)

### session_debt_auction_ambush.jsonl
- **Generated:** 2025-10-31 (pre-bugfix)
- **Purpose:** Integration testing, ML training data
- **Config:** session_config_combat.json
- **Known Bugs:** Status effect targeting (Bug #1)
- **Keep Because:** Historical value, agent behavior documentation
- **Use For:** Regression testing, ML training, bug documentation
```

## Workflow Example: Fixing a Bug

1. **Identify bug in existing fixture**
   ```bash
   grep "Condition (Riven Ashglow): Stunned" tests/fixtures/sessions/session_debt_auction_ambush.jsonl
   # Found! Bug confirmed.
   ```

2. **Document the bug**
   - Add entry to `tests/fixtures/sessions/bugs/status_effect_targeting.md`
   - Note affected events, characters, expected vs actual behavior

3. **Create targeted test config**
   - Create `session_config_status_effect_test.json`
   - Minimal, focused config to reproduce bug

4. **Fix the code**
   - Implement fix in `dm.py`
   - Write unit tests for the fix logic

5. **Generate new fixture**
   ```bash
   python3 scripts/run_multiagent_session.py \
     scripts/session_configs/session_config_status_effect_test.json

   # Move output to fixtures
   mv multiagent_output/session_*.jsonl \
     tests/fixtures/sessions/session_status_effect_test.jsonl
   ```

6. **Verify fix**
   ```bash
   # Check new fixture doesn't have bug
   grep "Condition (Test Caster): Stunned" tests/fixtures/sessions/session_status_effect_test.jsonl
   # Should find NOTHING (or only enemy conditions)
   ```

7. **Update tests**
   - Update integration tests to use new fixture for positive cases
   - Keep old fixture tests for regression/documentation

8. **Update documentation**
   - Add to `tests/SESSION_NOTES.md`
   - Update fixture README
   - Commit everything with clear message

## For ML Training Data

**Important:** For machine learning training:

- **Keep buggy data!** It shows real agent behavior
- **Label it clearly:** Add metadata indicating it contains bugs
- **Generate clean data too:** For comparison and validation
- **Track provenance:** Always know which code version generated which data

```jsonl
{"event_type": "metadata", "code_version": "v1.0.0-pre-bugfix", "contains_bugs": ["status-effect-targeting"], "use_for": "behavior_analysis_only"}
```

## Summary

**Default Strategy for This Project:**

1. ✅ **Keep original fixtures** - Historical/ML value
2. ✅ **Generate new targeted fixtures** - Test specific fixes
3. ✅ **Document known bugs** - In fixture metadata and separate docs
4. ✅ **Test both behaviors** - Verify old bug, verify new fix
5. ✅ **Clear lineage** - README explains which fixture is which

**File organization:**
```
tests/fixtures/sessions/
├── README.md                                    # Fixture catalog
├── session_debt_auction_ambush.jsonl            # Keep - has documented bugs
├── session_status_effect_test.jsonl             # New - targeted bug test
└── bugs/
    └── status_effect_targeting.md               # Bug documentation
```

This approach maintains historical accuracy, enables regression testing, preserves ML training data, and provides clear test cases for fixes.
